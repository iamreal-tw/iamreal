# 電路檢查憑證的金鑰用途

電路檢查憑證的金鑰用途是簽章（`digitalSignature`），而且只有這一項。PSE 的電路沒有這項檢查。

## 為什麼

不檢查金鑰用途，一張卡片有兩個匿名編號。

- **卡片上有兩張內政部簽發的憑證、兩把金鑰**：簽章用（金鑰用途 `digitalSignature`）和加密用（`keyEncipherment`、`dataEncipherment`）。兩張由同一把發證金鑰簽發，效期相同，除了金鑰用途和金鑰本身，結構完全相同。
- **卡片肯用加密金鑰簽章。** 卡片的簽章指令是對一個 256 位元組的區塊做一次私鑰運算，卡片對加密金鑰照樣執行。

我們用一張現役的第二代卡片實測過（2026-11-14）：指定加密金鑰簽一段測試文字，卡片回了簽章，這個簽章用加密用憑證的公鑰驗得過。卡片的金鑰目錄把這把金鑰標示成不可簽章，但卡片不照這個標示執行。

所以拿加密用的憑證配加密金鑰的簽章，證明一樣成立，匿名編號和簽章用的那一組不同。「一張卡片一個名額」會變成兩個。

## 做法

- ADR-0009 已經走到公鑰欄位。這裡接著往下走：公鑰的指數，然後是延伸欄位。
- **內政部簽發的用戶憑證，延伸欄位的順序是固定的**：發證者金鑰識別碼、主體金鑰識別碼、金鑰用途，之後才是憑證政策、主體目錄屬性、廢止清冊和發證者資訊的網址。前兩個的長度固定，所以金鑰用途的位置可以從結構推導，不需要裝置提供。
- 電路把這一段釘死：指數是 65537；延伸欄位的外層標頭；發證者金鑰識別碼和主體金鑰識別碼的標頭（各自 20 個位元組的內容不看）；金鑰用途整個欄位等於 `30 0e 06 03 55 1d 0f 01 01 ff 04 04 03 02 07 80`，也就是 critical、只有 `digitalSignature`。
- 一張憑證只能有一個金鑰用途欄位，所以釘住第三個就夠了。
- 讀取的範圍不能超出簽過章的憑證內容。

延伸欄位的順序是用三張真的憑證核對的：PSE 測試資料裡的一張、我們自己的一張現役卡（G3 發證金鑰簽發）、一張過期的舊卡（G2 發證金鑰簽發，展期過）。三張的順序相同。

## 測試

簽章用的憑證通過；加密用的憑證、多種用途並列、沒有金鑰用途、金鑰用途不在第三個位置，都被拒絕。先放一個加密用途、後面再放一個簽章用途的憑證也被拒絕，確認電路看的是結構上的位置。在金鑰用途中間截斷的憑證被拒絕。

對照用的 PSE 電路分支上也加了同一項檢查，逐案比對的結果相同（ADR-0012）。

## Considered Options

- **不在電路裡檢查，由後台或讀卡的程式保證用的是簽章金鑰**：後台看不到憑證；讀卡的程式在持卡人的裝置上，持卡人可以換掉。
- **位置由裝置提供，電路檢查那裡長得像金鑰用途**：延伸欄位的順序不同也能用。但裝置可以指到別處長得一樣的位元組，和 ADR-0009 要避免的是同一類問題。
- **在延伸欄位裡逐一找金鑰用途**：不依賴順序，但電路複雜很多，更難檢查。內政部的順序目前是固定的，先不需要。
- **改檢查憑證政策或主體目錄屬性**：簽章用和加密用的憑證這兩欄相同，分不出來。

## Consequences

- 加密用的憑證過不了卡。持卡人不受影響：平常過卡用的本來就是簽章金鑰。
- **延伸欄位順序不同的憑證會被拒絕。** 這是看得見的失敗。政府的憑證格式文件寫明延伸欄位「實際在憑證中的順序可能不是照以下的順序」，所以我們依賴的順序是觀察到的，不是規格保證的。內政部改變簽發格式時，電路要跟著改，改之前新格式的卡片過不了卡。上線前要用更多不同年份的卡片試過，尤其是 2017 年以前的格式和第一代卡片。
- 指數不是 65537 的憑證會被拒絕。
- 卡片上還有第三把可以簽章的金鑰（代號 `SIGN02`），我們看過的兩張卡片上都沒有對應的憑證，所以過不了卡。它的用途我們不知道；內政部如果替它簽發憑證，而且金鑰用途也是簽章，這項檢查擋不住，要重新評估。
- 這個問題已經回報給 PSE（[ethereum/zkID#118](https://github.com/ethereum/zkID/pull/118)）。
