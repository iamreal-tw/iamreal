# 持卡人裝置上的保護，不由伺服器決定

一條限制如果是在保護持卡人、對抗伺服器，就寫死在持卡人的裝置上。伺服器可以讓它更嚴，不能讓它更寬。

伺服器在這個系統裡能做很多事：發題目、提供清冊的鏡像、收證明、寫名冊。持卡人的匿名性不能依賴伺服器守規矩（`CLAUDE.md` 的硬限制：匿名編號只有持卡人算得出來）。凡是「伺服器給了不同的值，就能知道持卡人是誰，或把他在不同平台的身分連起來」的地方，那個值都要由裝置自己決定或自己檢查。

## 目前用到的地方

| 限制 | 伺服器能決定的話，會怎樣 | 裝置怎麼做 |
|---|---|---|
| 卡片簽哪個場合字串 | 讓卡片多簽另一個平台的場合字串，就拿到持卡人在那個平台的匿名編號，把兩邊的身分連起來 | 持卡人在畫面上選平台，程式用寫死的對照表換成場合字串（`spec/scope.md`），不從伺服器的回應裡拿 |
| `current_time` | 伺服器挑時間，每次過卡問「憑證在這個時刻有沒有效」，約 28 次就能二分出憑證的生效時刻到秒，內政部能據以對到人 | 裝置用自己時鐘的台灣日期；題目上的日期不是今天就不過卡（`spec/challenge.md`） |
| 廢止清冊多舊還能用 | 鏡像給某人一份舊清冊，從他過不過得了卡，知道他的卡那時是否暫時停用過 | 取伺服器公布的天數和內建 7 天中較小的，並記住看過的最高清冊編號（ADR-0015） |
| 廢止清冊的樹 | 樹裡多塞幾個嫌疑人的序號，從過不過得了卡指出持卡人 | 裝置自己驗內政部的章、自己建樹（ADR-0015） |

過卡失敗的原因只顯示給持卡人，不回報伺服器。

## 代價

- **原生 app 要使用者手動更新。** 寫死的規則要等更新才會改，所以之後可能放寬的限制，裝置一開始就訂寬一點，放寬時只動伺服器和規格（ADR-0015 的 7 天就是這樣訂的）。要收緊時，舊版 app 照樣會做出伺服器會拒絕的證明，那是看得到的失敗，不會害到持卡人。
- **網頁版的頁面也是伺服器送的。** 頁面和 API 從同一台伺服器來時，這條原則擋不住營運者本人：改過的頁面可以照它想要的方式做。它擋得住的是 API 被入侵、或之後頁面和 API 分開部署時的其中一邊；它也讓公開的 `web/` 程式碼看得到這些規則。對外說「營運者算不出匿名編號」時，網頁版的前提是用的頁面就是公開的那一份；原生 app 的前提是安裝的是公開程式碼編出來的那一版。

## Considered Options

- **伺服器在回應裡告訴裝置要用什麼值**（場合字串、時間、清冊的上限）：最有彈性，但這些正是伺服器拿來探測持卡人的工具。
- **裝置照伺服器的值，但事後由重驗的人檢查**：探測不需要成功的證明，失敗的過卡不會留在名冊上，重驗的人看不到。

## Consequences

- 寫裝置上的程式（`web/`、`android/`、`ios/`）時，每一個從伺服器拿到的值都要問：伺服器換一個值，能不能藉此知道持卡人是誰？能的話，就照這份決定處理。
