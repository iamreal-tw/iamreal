# 平台表由後台給，裝置只編輯自己認得的平台

每次過卡，裝置向後台拿一次平台表（`GET /api/v1/config`）：這份名冊現在收哪些平台、每個平台的帳號名稱是什麼格式。裝置自己也有一份平台的定義：顯示名稱、帳號怎麼寫（Threads 是前面加 `@`）、預覽個人檔案開的網址、格式不對時的提示。這些寫死在裝置上，不從後台拿。

持卡人能編輯的，是兩邊都有的平台：

| 後台的表 | 裝置的定義 | 這張卡片在那裡有帳號 | 畫面 |
|---|---|---|---|
| 有 | 有 | 都可以 | 一列，可以填、改、清空 |
| 有 | 沒有 | 有 | 一列，顯示平台代號和帳號，不能改、不能清空；送出時原樣放回清單 |
| 有 | 沒有 | 沒有 | 不顯示 |
| 沒有 | 有 | | 不顯示 |

名冊接受哪些平台、什麼格式，是規格的平台表決定的（`spec/scope.md`），每個重驗的人手上都有。後台給的那一份只是方便。

第一次上線，平台表只有 Threads。

## 為什麼平台表由後台給

- **裝置上寫死的表會過時。** 原生 app 要使用者手動更新（ADR-0016）。平台的定義可以先隨 app 出去，等後台的表列出那個平台才出現在畫面上；帳號名稱的格式放寬時，也不用等 app 更新。
- **相信這張表，不會讓後台認出持卡人。** 表對每個人都一樣，裝置照它做的只有「顯示哪幾列」和「檢查帳號名稱的格式」。後台多報一個名冊不收的平台、給一個比較寬的格式，做出來的紀錄寫不進名冊，或讓整份名冊不成立，重驗的人看得到。最壞是持卡人白做一次過卡。

## 為什麼顯示名稱寫死在裝置上

顯示名稱是持卡人決定「這個帳號要宣告在哪裡」時唯一看得懂的東西。後台把代號 `threads` 的名稱寫成另一個服務，持卡人就會把帳號宣告在他沒有打算宣告的平台上，而紀錄公開之後收不回來（ADR-0004）。這屬於「保護持卡人、對抗伺服器」的限制，所以由裝置決定（ADR-0016）。

代價是裝置不認得的平台，它沒有名稱可以顯示，也不知道帳號怎麼寫，所以不讓持卡人編輯。

## 為什麼不認得的平台原樣保留

一筆紀錄寫的是這張卡片的整份帳號清單（ADR-0017），清單裡沒有的帳號就是收回。裝置把不認得的平台丟掉，持卡人用舊版的 app 過一次卡，就會在不知情的情況下收回他在新版 app 裡宣告的帳號。

所以那個帳號原樣放回清單，放在它在清單順序裡的位置；畫面顯示成一列不能修改的，寫著平台代號和帳號。確認的畫面列出整份要簽的清單，這一列也在。

## Considered Options

- **平台表只寫死在裝置上**：見「為什麼平台表由後台給」。
- **顯示名稱也從後台拿**：見「為什麼顯示名稱寫死在裝置上」。
- **不認得的平台不送出**：等於替持卡人收回，見上一節。

## Consequences

- 加一個平台要做兩件事：規格的平台表加一列，裝置加一份定義。兩邊都有，持卡人才填得到。
- 裝置讀不到平台表、讀不懂這張卡片的現況時，不往下：沒有現況就建不出清單。
- 帳號名稱的格式固定寫成一個字元集加一個長度範圍（`[…]{m,n}`），裝置只認這一種形式，不需要完整的正規表示式；讀不懂格式的那一列，當成不認得的平台。
- 裝置不認得的平台，帳號名稱沒有格式可以檢查。裝置只檢查每個平台代號和帳號名稱都要符合的最低條件，不符合就不往下。
- 後台回的現況少報一個帳號時，裝置擋不住：做出來的清單少了它，就是收回它。持卡人在確認的畫面看得到整份清單；公開的名冊也看得出後台答錯了什麼。
- 卡片簽哪個場合字串，仍然不從後台拿（ADR-0016）。
- 持卡人在確認的畫面看到的是裝置的顯示名稱；不認得的平台看到的是代號。
