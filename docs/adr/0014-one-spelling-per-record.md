# 名冊的每一筆紀錄只有一種寫法

名冊檔案的每一行是一筆紀錄：一個固定的樣板，填入 10 個欄位的值，鍵的順序固定、沒有空白、沒有跳脫字元，以一個換行結尾。每個欄位的值也只有一種寫法：證明是固定長度的標準 base64，解碼再編碼要得到同一個字串；題目和匿名編號的補零位元必須是 0；樹根小於體的模數；帳號清單照平台代號由小到大排，每個平台最多一次，每一項也是固定的樣板（ADR-0017）。所有的值都限定在不含引號、反斜線、控制字元的 ASCII；帳號清單裡的引號只出現在它的樣板放的位置。

檢查一行，是用任何方式解析它、檢查每個值，再照樣板重寫一次，和原本那一行逐位元組比對。不一樣，就是寫法錯了。

## 為什麼

名冊的價值在於任何人都能下載、照公開的規則重算，得到和營運者一樣的答案（ADR-0005）。要做到這一點，同一份名冊在不同人手上必須讀成同一組事件。

我們讓兩個只讀規格文字的程式各自實作一次，比對結果。允許 JSON 各種寫法的版本出了這些問題：

- **同一行讀成兩個事件。** `{"username":"alice", …, "username":"bob"}` 這種重複的鍵，有的 JSON 解析器取第一個，有的取最後一個。營運者可以發一行讓 Python 讀成 alice、讓 Go 讀成 bob 的紀錄，兩個重驗的人看到不同的事件，各自都以為自己驗過了。（這是當時的格式；現在帳號寫在帳號清單裡，同一個問題換成「同一個平台出現兩次」，同樣由只有一種寫法擋掉。）
- **解析器之間的差異列不完。** Go 標準函式庫的 JSON 解析器把 `"Username"` 當成 `username`；`null`、CRLF、檔案開頭的 BOM、跳脫字元、`1.0` 和 `1e0` 這類數字，各家的處理都不同。逐項列規則永遠有漏的。
- **一筆紀錄有好幾種位元組。** 證明的 base64 有好幾種寫法能解出同樣的位元組，題目最後一個字元有四種寫法。同一個事件可以用不同的位元組出現兩次，「一個題目只能用一次」的檢查也會被繞過。

規定只有一種寫法，再逐位元組比對，上面這些一次全部擋掉，不必知道每一種解析器的毛病。

## 錯誤分兩層

- **寫法錯**（任何一行不合樣板、任何欄位格式不對、帳號清單的順序不對、同一個平台出現兩次、列了平台表以外的平台、`seq` 不連續、`prev` 對不上）：整份名冊不成立，重驗的人不從它算任何現況。
- **寫法對，但證明驗不過或違反名冊規則**：那一筆無效，照樣列出，不改變任何狀態。

分兩層，是因為後一種本身就是證據：營運者寫入了不該寫入的事件，重驗的人看得見，也知道是哪一筆。前一種則是檔案本身不可信，沒有辦法逐筆判斷。

## Considered Options

- **雜湊只算欄位的值，JSON 的寫法不限**：重新排版過的名冊照樣驗得過。這是原本的設計，對照實作時改掉，理由見上。重新排版只是方便，沒有人需要。
- **只禁止重複的鍵，其他照 JSON 的規則**：只補了找到的那一個洞。後來又找到大小寫不同的鍵、`null`、換行等差異，表示這條路要一直補。
- **用標準的正規化 JSON（例如 RFC 8785）**：也能做到一種寫法，但實作要正確處理數字和 Unicode 的正規化，比填樣板複雜得多，而我們的欄位本來就只有整數和限定字元的字串。
- **用二進位格式**：沒有解析器差異的問題，但名冊要讓人打開來就看得懂，JSON Lines 用一般的文字工具就能讀。
- **任何一筆無效就讓整份名冊不成立**：一筆壞紀錄（最可能是程式錯誤）就會讓所有人的重驗停擺，而且看不出問題出在哪一筆。

## Consequences

- 實作檢查一行時，不能只用 JSON 函式庫解析就算數，一定要照樣板重寫比對。`spec/record.md` 寫了做法，`spec/vectors/record.json` 列了寫法錯的行、寫法對的行和整份的名冊檔案。
- 欄位的格式只能放寬，不能收緊。放寬（例如帳號名稱多允許一種字元）時，舊的紀錄仍然合格；收緊會讓舊紀錄變成寫法錯，整份名冊不成立。
- 帳號名稱的格式依平台定，平台代號和場合字串各有固定的格式（`spec/scope.md`），都不能含引號、反斜線、控制字元，所以樣板不需要跳脫。之後開放的平台如果帳號名稱需要這些字元，要改這份決定。
- 名冊的檔案和雜湊鏈（ADR-0005）講的是同一串位元組，任何兩份通過檢查的名冊，鏈尾相同就是同一份檔案。
- **正常營運的名冊上不會有任何無效的紀錄。** 後台寫入前就驗證證明、套用規則；無效的紀錄只會來自營運者寫入了不該寫入的事件、我們自己的程式錯誤，或廢止清冊的存檔缺了某一份（那筆紀錄的樹根就無法被承認）。後台每次發布快照前，自己用 `roster/` 完整重算一次，出現任何無效的紀錄就停止發布、先查原因。
