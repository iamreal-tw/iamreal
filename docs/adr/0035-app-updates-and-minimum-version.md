# app 能跑什麼由安裝檔決定；太舊的 app 讀到最低版本後自己停

手機 app（Android、iOS）只經過商店更新。這一份定三件事：哪些東西內建在 app 裡，太舊的 app 怎麼停下來，改電路或改紀錄規則時商店的審查怎麼排進生效日（ADR-0031）。

## 內建的和後台給的

| 東西 | 放哪裡 |
|---|---|
| 電路檔、驗證金鑰、參數檔的 SHA-256 | 寫死在 `device-core/` |
| 電路檔（0.63 MB、0.80 MB）、驗證金鑰（各 3,680 個位元組）、參數檔（8 MiB） | 包進 app；核心用之前照樣核對 SHA-256（ADR-0034） |
| 場合字串 | 寫死（ADR-0016） |
| 發證金鑰 | 寫死，後台不能加 |
| 介面文字 | 全部內建；後台不送任何顯示給持卡人的字 |
| 紀錄規則和它用到的數字 | 內建在 `device-core/`，跟著紀錄規則的版本走 |
| 平台表 | 後台給（ADR-0019） |
| 清冊最多舊幾天 | 後台給，裝置取它和內建 7 天中較小的（ADR-0015） |
| 最低版本 | 後台給，見下一節 |

一個版本的 app 能跑哪幾份電路、照哪幾版紀錄規則算，由安裝檔決定。換電路、換場合字串、加發證金鑰、改紀錄規則，都要出新版 app。

## 最低版本

`GET /api/v1/config` 給 Android、iOS 的 app 各一個最低版本和它的起算日：

```json
"min_app": {
  "android": { "build": 12, "from": "2027-03-01" },
  "ios": { "build": 9, "from": "2027-03-01" }
}
```

- `build` 是商店的整數版本號：Android 的 `versionCode`，iOS 的 build number。兩個 app 各自一個數字。
- app 的版本比 `build` 小時：起算日之前照常過卡，先顯示從哪一天起這一版不能過卡；起算日當天起，在要 PIN、感應卡片之前停下來。日期用裝置自己時鐘的台灣日期，和 `current_time` 同一個來源（ADR-0016）。
- 這個欄位讀不懂就不往下，和讀不懂平台表相同（ADR-0019）。
- 第一版 app 就有這個檢查。
- 後台收證明時不看版本。請求帶的客戶端參數照舊只用來計數（ADR-0032）。

停下來的畫面只有內建的內容：這一版不能過卡了，要更新；卡片還沒被讀取，沒有東西送出去；一個按鈕開商店的頁面；另一條路是用讀卡機走網頁版。畫面不講這一次為什麼調高，理由在網站的公告。

最低版本的數字寫在這個程式庫的一個檔案裡，每次調高是一個 PR，說明裡寫理由，照 ADR-0029 部署。對人的公告併在改規則的公告裡（ADR-0031），多一句 app 要更新到哪一版。正式網站和測試網站（ADR-0028）各有自己的值。

## 商店的審查和生效日

用生效日 D 的紀錄規則修改（ADR-0031），多一個條件：**D 之前，新版 app 已經在兩個商店都下載得到**。最低版本的起算日就是 D。

- 新版 app 內建新舊兩版規則，照紀錄的日期切換，所以在 D 之前就能上架。
- 不另外留給使用者更新的時間。沒更新的人在 D 當天被擋下來。
- 寫 PR 時 D 預設抓合併後 10 天。Apple 的審查九成在 48 小時內；Google 沒有給一般情況的數字，只寫了某些帳號可能到 7 天或更久（[#84](https://github.com/iamreal-tw/iamreal/issues/84)）。
- 審查趕不上時，照 ADR-0031 另發一個 PR 把 D 往後延。
- 規則有漏洞、app 還在審的那幾天，用後台的政策先擋（ADR-0031：後台可以不寫入紀錄規則會接受的紀錄）。

往回套用的修改（已經寫入的紀錄結果全部相同，沒有 D）如果會讓裝置算出不同的後果，同樣等新版在兩個商店上架後才調高最低版本。

改電路分兩種：

- **不是補漏洞**：後台一段期間內新舊兩份電路都收；新版上架後，舊電路從 D 起不收，最低版本同一天調高。
- **是漏洞**（ADR-0031 的例外）：後台立刻停收，不等商店。新版上架前 app 的使用者過不了卡，改用網頁版；Apple 那邊申請加急。

## 理由

- **電路是唯一同時看得到憑證、公鑰、兩個簽章的程式。** 後台能指定用哪份電路，就能給一份把憑證序號放進公開輸出的電路；`CLAUDE.md` 的硬限制就變成後台守規矩才成立。所以雜湊不從後台拿（ADR-0016）。網頁版本來就這樣做（`web/src/prover/artifacts.ts`）。
- **雜湊寫死之後，下載省不到更新。** 換電路一定要出新版 app；執行時下載只省安裝檔的大小（約 10 MB），卻多一步會失敗的下載，還要處理存檔被系統清掉的情況。每次過卡本來就要下載 6 到 17 MB 的清冊。
- **內建的檔案，拿到安裝檔的人就能核對。** 不用再去抓我們站上的檔案比。
- **紀錄規則是程式加數字。** 只下載數字，改到程式時還是跟不上。它也不能像清冊的 7 天那樣先訂寬：它要和證明紀錄算得一模一樣，訂寬就是算錯。
- **舊的規則會讓持卡人照錯的後果同意。** 規則用生效日改版之後，舊版 app 的確認畫面可能說錯後果，例如把會用掉一次更換的改動說成不會。這種紀錄合法，後台不會拒收，公開之後收不回來。只有裝置在簽章之前自己停才擋得住。
- **最低版本不是後台多出來的開關。** 後台本來就能拒收任何證明、不回 `config`。這個值對每個人都一樣，裝置照它做的只有「停」，而且在第一次簽章之前，沒有匿名編號，後台分不出是誰。伺服器只能用它讓裝置更嚴。最壞是後台騙人去更新；`config` 是公開的，調高的紀錄在 git 歷史裡。
- **不留更新的寬限期。** 被擋下來的人看到的是「要更新」，不是錯的後果；固定的公告期會讓規則的漏洞多被利用那麼多天（ADR-0031）。

## Considered Options

- **雜湊由後台給，或後台給一份簽過章的清單**：換電路不用更新 app。但前者是後台能換電路；後者是拿得到簽章金鑰的人能換電路，不經商店，沒有人能從安裝檔核對，和不做不經商店的程式更新是同一個理由（[#83](https://github.com/iamreal-tw/iamreal/issues/83)）。
- **電路檔和參數檔執行時下載，雜湊寫死**：安裝檔小約 10 MB，見「理由」第二點。
- **紀錄規則的數字由後台給**：見「理由」第四點。
- **後台看客戶端報的版本拒收**：版本是客戶端自己報的，擋不住改過的 app；在簽章之後才擋；也擋不到後台不會拒收的那一種（後果顯示錯）。
- **不擋，舊版照樣過卡**：ADR-0016 原本的說法是舊版會做出後台拒收的證明、是看得到的失敗。對電路成立，對紀錄規則不成立。
- **後台公布現在的規則版本和收哪些電路，裝置自己比對**：理由可以對著規格檢查，但擋不到只出在 Kotlin 或 Swift 的錯。兩種都做是兩套要檢查的機制。
- **兩個 app 共用一個版本號**：只有一個 app 出錯時，另一個 app 的人也要更新。

## Consequences

- **每一次用生效日的規則修改，最快也要等兩個商店審完。** 規則的漏洞能被利用的時間，從 ADR-0031 的 3 天變成看商店；中間靠後台的政策擋。
- **`config` 的 `min_app` 怎麼讀，第一版 app 上架後就改不了。** 寫進 `docs/api/` 和 `spec/`；讀法有標準答案（ADR-0034：裝置上的檢查先補進 `spec/`）。
- **`device-core/` 和兩份後台以外的實作一樣，永遠留著用過生效日的每一版規則**（ADR-0031）。
- **改過的 app 可以不理最低版本。** 它送的證明照紀錄規則收或不收；最低版本保護的是用商店那一版的人。
- **裝置的時鐘不對時**，起算日前後可能早停或晚停一天；題目上的日期不是今天本來就不過卡（ADR-0016）。
- **網頁版沒有最低版本。** 頁面每次都從伺服器拿。開著不關、跨過 D 的分頁怎麼辦，這一份沒有定。
- `CONTRIBUTING.md` 加一條（`device-core/` 建好時）：改紀錄規則、電路、場合字串表的 PR，寫明舊版 app 算出來的結果會不會不同；會的話，同一個 PR 調高最低版本。
- ADR-0016 的表加兩列（跑哪一份電路；這一版 app 還能不能過卡），「代價」那一段跟著改。
- 停下來的畫面和「某月某日起不能過卡」的用字，在手機過卡的畫面那張票定，寫進 `design/copy/`。
