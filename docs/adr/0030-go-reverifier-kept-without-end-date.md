# Go 的重驗工具不設期限，改規則時兩份實作一起改

`verifier/`、`roster/`、`crl/`、`cmd/` 的 Go 程式不設期限：名冊還在收過卡，就留著當後台以外的第二份實作（ADR-0023），每天的重驗用它跑（ADR-0025）。

名冊規則因此有兩份實作：Go 的 `roster/`，和 TypeScript 的那一份（後台和裝置共用）。要改規則時，`spec/roster-rules.md`、`spec/vectors/`、Go、TypeScript 在同一個 PR 改好，名冊規則的版本號加一號；兩邊的測試都讀改過的 `spec/vectors/`，全部通過才合併、部署。不接受 TypeScript 先上、Go 之後跟上。

## 什麼時候重新討論

出現下面任何一種情況時，重新討論留不留：

- 上線之後，規則還是改得很頻繁，兩份一起改的負擔明顯拖住其他工作。
- 沒有人能審 Go 的改動，只能照收。這樣的第二份實作只是形式上的。
- 外面有人寫了另一份獨立的實作。

要拿掉 Go，前提是先有另一份獨立的實作（外面的人寫的，或用別的語言重寫的），而且能照 ADR-0025 每天跑。沒有替代的就繼續留著；真的留不住，就照實說「後台和重驗工具不會錯在一起」這件事沒有了，ADR-0025 重開。只靠 `spec/vectors/` 的標準答案不算替代。

## 兩份實作獨立到哪裡

獨立的是證明以外的部分：公開輸入的檢查、紀錄的讀法、名冊規則、廢止清冊的樹。

證明的密碼學驗證不獨立。後台用 WASM 版的 Barretenberg，Go 的重驗呼叫原生的 `bb`，兩邊是同一份 C++ 程式碼編出來的；Barretenberg 接受了不該接受的證明，兩邊會一起錯。這一層靠的是 Noir 和 Barretenberg 本身，以及版本釘住。之後出現持續維護、和 Barretenberg 無關的 UltraHonk 驗證程式，再考慮加進每天的重驗。對外說明兩份實作互相檢查時，照實寫出這一層。

## 理由

- **收錯的紀錄是永久的，只有另一份實作看得出來。** 收錯的一筆照樣列在公開的名冊上（ADR-0014），錯的卡片狀態會一路影響後面的結果。後台重寫之後，後台和裝置用同一份 TypeScript 的規則，它寫錯了兩邊一起錯。
- **兩份實作已經抓到過標準答案沒抓到的問題。** 照規格的文字另寫一份時，找到十幾處兩種讀法都說得通的地方，其中幾處會讓兩份實作算出不同的結果，例如 Go 的 JSON 解析器把 `Username` 當成 `username`；Go 的程式記了最近 5 個日期的筆數，規格的狀態表卻漏寫了這一項，後來改成 ADR-0024。這些當時都不在標準答案裡。
- **多出來的維護主要在規則，而且不大。** 紀錄的格式、匿名編號、清冊的樹照規格寫，上線後很少改；匿名編號的算法不動（ADR-0012）。上線前幾次改規則，Go 的 `roster/rules.go` 改動 39 到 66 行；改紀錄格式的那一次改動 371 行，加上 `verifier/` 約 400 行。大部分的工作在規格和標準答案，不管留幾份實作都要寫。
- **上線之後規則會改得少。** 已經有效的紀錄不能因為改規則變成無效。
- **一起改好才生效，是 ADR-0025 本來就要的。** 後台照新規則收、Go 還照舊規則，隔天的重驗會把新收的紀錄判成無效或卡片狀態比不上，營運者就要停止收過卡。剛改規則的幾天最容易出錯，也是最需要第二份實作的時候。
- **照條件重新討論，不照日期。** 定一個檢討日，到時候沒有新的理由也要再決定一次。

## Considered Options

- **設一個檢討日（例如上線滿一年）**：到時候不一定有新的事實，只是多一次決定。
- **TypeScript 的後台通過逐案比對後，只靠 `spec/vectors/`**：標準答案只檢查列出來的案例；上面那些問題是另一份實作照規格寫的時候才找到的。固定種子的隨機長序列要有一份實作當答案，沒有第二份就沒有答案可比。
- **TypeScript 先上，Go 之後跟上**，這段期間每天的重驗暫停名冊規則那一段：改得快，但只有一份實作在跑的那幾天，就是剛改完最容易錯的時候。
- **要拿掉 Go 時再決定用什麼補**：想拿掉 Go 時，通常是因為維護不動了，那時候最不適合判斷該留什麼保證。
- **現在就找第二份證明的驗證程式**：要防的是這個專案自己的程式寫錯；Barretenberg 寫錯是它整個生態系的問題，第二份實作本來就不是為它留的。

## Consequences

- **改規則的 PR 一次動四個地方**：規格、標準答案、Go 的 `roster/`、TypeScript 的規則。`CONTRIBUTING.md` 寫明。
- **Go 要有人能審。** 營運者審不了 Go 的改動時，就是重新討論的時候。
- **對外的說明不能只寫「兩份獨立的實作」**，要寫出證明的密碼學驗證兩邊共用 Barretenberg。
- **ADR-0025 的前提留著。** 那份 Consequences 裡「Go 的重驗指令是這個做法的前提」那一條改成指向這一份。
- **上線之後改規則時，已經寫入的紀錄照哪一版算**，在[上線之後改名冊規則，已經寫入的紀錄照哪一版算](https://github.com/iamreal-tw/iamreal/issues/40)決定。
