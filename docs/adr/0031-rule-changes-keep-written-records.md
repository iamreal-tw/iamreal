# 改紀錄規則不改變已經寫入的紀錄

> 補充：有手機 app 之後，生效日 D 之前新版 app 要已經在兩個商店都下載得到；改電路時商店的審查怎麼排，見 ADR-0035。

上線之後改紀錄規則，已經寫入的紀錄有兩件事不變：每一筆的結果（有效或無效、種類、代碼），和每一行都格式正確。

新規則預設往回套用到所有紀錄，前提是照新規則算，已經寫入的紀錄結果全部相同；這時舊版的規則可以刪掉。有任何一筆不同，新規則就從一個生效日 D 起生效：紀錄的日期（題目裡的日期）在 D 當天或之後的照新版算，之前的照舊版算。

## 怎麼做

- **規格寫明這個承諾和生效日的做法。** 規則的版本表（每一版從哪一天起）和照日期切換版本的程式，第一次需要生效日時才加；加的那一次不改變任何紀錄的結果。版本的編號就是 ADR-0025、ADR-0030 說的紀錄規則的版本號。
- **用了生效日，兩份實作都永遠留著每一版。** 從第 1 筆重算、從紀錄重建每張卡片的狀態，都照每一筆紀錄的日期選版本。
- **一張卡片不會從新版回到舊版。** 一張卡片的日期只會持平或往後（ADR-0024）。不同卡片之間，D 前後的紀錄照序號排會交錯，結果還是固定的。
- **D 至少比正式網站的部署晚 3 天**，合併時在網站上公告 D，不另外定公告期。部署趕不上時，在 D 之前另發一個 PR 把 D 往後延。
- **兩道比對。** 改規則的 PR 在合併前，拿最新的正式的證明紀錄用新舊兩版各算一次，逐筆比結果，寫在 PR 的說明裡：全部相同才往回套用，否則用生效日。部署之後，版本號加一號觸發的整份重驗（ADR-0025）是最後一道：從那份證明紀錄到部署之間寫入的紀錄比出不同，照 ADR-0025 停止收過卡，退回舊版的程式，改用生效日重發。
- **規格的表只放寬、只新增。** 平台表的帳號格式、平台代號、場合字串表都不收緊、不刪除。帳號格式不符會讓那一行格式錯誤、整份紀錄檔壞掉（`spec/record.md`），檢查格式在套用規則之前，生效日救不了。外部平台把帳號改嚴時，表上維持原本的格式；新的宣告要不要擋，是後台自己的規則。
- **後台自己的規則不在這個承諾裡。** 後台可以不寫入紀錄規則會接受的紀錄（`spec/record-rules.md`，「Not part of these rules」）；這種規則改了，不影響已經寫入的紀錄。

## 唯一的例外：證明本身不再可信

電路少了限制、Barretenberg 接受了不該接受的證明、內政部的發證金鑰外洩：有人能大量產生合法的證明時，偽造的紀錄和真的一樣能重驗，承諾不能讓它們永遠有效。

- 作廢的條件要能從公開的資料算出來：目前只有「某一版電路的紀錄」（每筆紀錄帶著自己的 `circuit`）或「全部的紀錄」。不挑日期，因為不知道是從哪一天開始；不由營運者認定某幾筆是假的，因為重驗的人無從檢查。
- 營運者先停止收過卡（ADR-0025）。要整批作廢、保留匿名編號，還是重來（換場合字串，`spec/scope.md`「Starting over」），看漏洞的性質決定，另寫一份 ADR。
- 作廢的機制等真的發生時才加；這個例外和它的界線，第一版的規格就寫明。

## 理由

- **公開的結果不被改寫。** 證明紀錄頁和島民證明的頁面上的「換過幾次」、每一筆是更換還是更正，寫入之後就是公開的事實。放寬的改法往回套用，也會把過去的更換改算成更正。
- **判斷簡單，任何人都能檢查。** 「新舊兩版算出來逐筆相同」是一個比較，不是判斷；整份重驗本來就會在版本號加一號時跑。
- **平常的修改只留一份規則。** 大多數修改（加平台、放寬上限）往回套用結果不變，不必留舊版；只有真的會改變過去結果的修改，才付出兩份實作永遠留著舊版的代價。
- **生效日可以事先定好、對外講得清楚。** 寫 PR 時就知道 D，規格、標準答案、Go、TypeScript 能在同一個 PR 改好（ADR-0030）；公告寫「某月某日起」，持卡人看得懂。
- **例外不能用來針對人。** 營運者能作廢單一的紀錄，就會被要求作廢某個人的宣告；規則做不到，比營運者不願意做更能擋住壓力。作廢的條件只能是任何人都能從證明紀錄算出來的事。

## Considered Options

- **只保證有效的紀錄不變成無效，種類可以重新算**：放寬的改法可以往回送給所有人。沒有採用，因為公開的種類和次數會被改寫，而「算不算只是重新解讀」說不清楚。
- **不做承諾，一律往回套用**：上線後就不能收緊任何規則，否則已經有效的紀錄會變成無效。
- **會改變過去結果的修改一律不做**：最省事，但遇到規則的漏洞只能不修。
- **生效點用序號（第 N 筆起）**：`spec/scope.md` 讓場合字串退場時這樣寫。沒有採用，因為寫 PR 時不知道部署時寫到第幾筆，要部署後再補一個 PR，違反 ADR-0030；對外也沒辦法公告「從第 N 筆起」。
- **固定的公告期（例如 14 天），或補漏洞和收緊分開定**：規則有漏洞時多被利用兩週；分開定又要營運者判斷一個修改算哪一種。
- **讓營運者作廢能證明是假的單一紀錄**：零知識證明看不出哪一筆是偽造的；能指出來的，只有營運者的判斷，重驗的人無從檢查。

## Consequences

- `spec/record-rules.md` 加一節寫這個承諾、生效日和例外；`spec/scope.md` 寫明表只放寬、只新增。
- `CONTRIBUTING.md`：改紀錄規則的 PR 附上新舊兩版在最新的正式的證明紀錄裡的逐筆比較，和往回套用還是用生效日。
- 第一次用生效日時，Go 的 `prooflog/`、TypeScript 的規則、`spec/vectors/` 都要能照日期切換版本，標準答案加跨過 D 的案例。
- 有人能大量偽造證明時，證明紀錄裡看不出來，要靠別的訊號（例如新卡片的增加數量異常）；要看哪些訊號，在監控的票裡定。
