# 憑證證明的電路加上效期檢查

憑證證明的電路（`certChain`）加一項檢查，確認憑證在過卡當天在效期內。這是我們對 PSE 的電路做的第一項修改，ADR-0001 因此從「原樣使用」改成「只加檢查，不放寬」。

我們會把這個問題回報給上游；上游收了，就回到釘住上游 commit、原樣使用。但不能假設這會發生：在那之前我們維護一個公開的分支，和上游的每一項差異各有一份 ADR。

理由是原樣使用時，過期的憑證過得了憑證證明：

- 電路不讀憑證的起訖日。以 commit `97210ba` 為準，`certChain.circom` 檢查的是發證單位的簽章、序號不在廢止清冊、公鑰一致。
- 廢止清冊不涵蓋過期的憑證。內政部憑證管理中心的憑證實務作業基準（v2.1）4.9.3.2 節寫廢止的憑證留在憑證廢止清冊「直至該廢止憑證到期為止」，4.10.1 節寫廢止資訊「須至該被廢止之憑證已過期後始可移除」。所以過期而沒被廢止的憑證不在清冊上，被廢止的憑證過期後也可以被移除。
- 電路用的廢止清冊快照只反映當下的清冊。產生快照的程式（[moica-revocation-smt](https://github.com/ethereum/moica-revocation-smt) 的 `server/cmd/smtbuild/main.go`，以 commit `e29d8f4` 為準）每次更新會把清冊上已經消失的序號從樹裡刪掉。

卡片沒有時鐘，過期後仍然能簽章。我們用一張已過期的卡片實測過（2026-11-14）：PIN 驗證通過，卡片照常簽章，簽章用卡片上那張憑證的公鑰驗得過。後果是：留著的舊卡片各是一個名額；掛失的卡片在憑證過期、從清冊移除後又能過卡。「一張卡片一個名額」和「上次過卡日會停住」這兩件事都會被削弱。

## 做法

- **電路多一個公開輸入 `currentTime`**：一個十進位整數 `YYMMDDHHMMSS`（UTC），和憑證裡 `UTCTime` 的 12 個數字同一種寫法，可以直接比大小。電路檢查 `notBefore <= currentTime <= notAfter`。
- **後台和重驗的人檢查 `currentTime` 對應題目裡的日期**：題目日期（台灣時間）當天的最後一秒，也就是題目日期的六位數字後面接 `155959`。憑證在到期日當天還能過卡，隔天不能。確切的規則寫進 `spec/`。
- **效期的位置完全從憑證的結構推導，不接受持卡人的裝置提供的位置。** 電路從頭走：外層標頭、版本、序號（讀長度）、簽章演算法（固定 15 個位元組）、發證者名稱（讀長度），下一個欄位就是效期。每一步都檢查標籤。PSE 的稽核報告（`audit_report_v3.md`）對「取出公鑰」指出的缺口是位置由裝置提供、只檢查位元組的樣子；這裡不沿用那種做法。
- **版本區塊寫死成 v3。** 現有的電路允許省略版本區塊；走結構需要序號在固定的位置。這是 PSE 的稽核報告已經建議的加固，也是這次差異的一部分。
- **只接受 `UTCTime`。** 到期日在 2050 年以後的憑證依規定改用 `GeneralizedTime`，電路會直接拒絕，不會算錯。內政部目前兩代發證憑證的效期分別到 2034 年和 2044 年。
- 場合簽章和宣告碼簽章用的電路（`userSig`）不動，匿名編號的算法不變。
- 連帶要改的：見證產生器、證明金鑰和驗證金鑰、驗證程式（公開輸入多一欄）、瀏覽器端準備輸入的程式。這套證明系統不需要可信設定，金鑰由電路照固定步驟產生。（這句話說的是 PSE 的電路用的 Spartan2；ADR-0012 改用的證明系統依賴一場通用的可信設定儀式。）
- 對外的說法是「用的是 PSE 公開的電路，加了一項效期檢查」，並指向差異。公布我們的電路、金鑰的雜湊和重現的步驟。
- 這項改動要另外請人檢查後才能用在正式的場合字串上。

## 量測

用 circom 2.2.3 編譯上游 `97210ba` 的電路和加了檢查的草稿（2026-11-14）：

| | 上游 | 草稿 |
|---|---|---|
| `certChainRS2048` 的約束數量 | 1,841,657 | 1,833,609 |
| `certChainRS4096` 的約束數量 | 2,033,081 | 2,025,033 |

效期檢查本身是 2,761 條。總數反而變少，是因為版本寫死之後序號的位置固定，原本在整份憑證裡選位置的約束被化簡掉了。新的公開輸入排在公開值的最後，原有的順序不變。金鑰可以重現：照上游的步驟在本機編譯 `certChainRS2048`、產生金鑰，驗證金鑰的 SHA-256 和上游驗證程式（`go-zkid-verifier` 的 `keymanager/keymanager.go`，commit `4bd1fdb`）裡釘住的值相同。我們的版本公布時用同樣的方式讓人核對。

草稿用上游的兩份測試資料跑過：效期內通過，早於 `notBefore` 一秒或晚於 `notAfter` 一秒都被拒絕。

## Considered Options

- **維持原樣，廢止清冊的快照改成歷來清冊的聯集**：擋得住掛失後過期的憑證，擋不住單純過期的憑證，而且只涵蓋開始存檔之後。
- **維持原樣，只接受目前還在簽發的那一代發證金鑰**：很粗，一代金鑰的簽發期間可能比憑證的效期長。
- **維持原樣，對外不說「有效的憑證」**：說法誠實，但名額的數量不再對應到有效的卡片。
- **位置由裝置提供，電路檢查那裡長得像效期**：改動更小，但和稽核報告指出的缺口是同一類。

## Consequences

- ADR-0001 的「一行都不改」改成「只加檢查，不放寬」。檔案雜湊不再和上游的發布相同。
- **要長期維護的東西變多**：電路、見證產生器、金鑰、瀏覽器端的證明套件、驗證程式都是自己的版本，放在自己的發布位置。上游修了別的問題時要自己合併。
- **回到上游可能很久不會發生。** 以 2026-11-14 為準：上游的程式庫已移到 [ethereum/zkID](https://github.com/ethereum/zkID)；`certChain` 在 `RSA-X.509-Cert` 分支上，最新的提交是 `97210ba`（2026-07-15）；我們沒有找到提到憑證效期的 issue 或 PR。
- 改動完成檢查、用在正式的場合字串之前，對外仍然只說憑證是「內政部簽發、不在廢止清冊上」，不說「有效」。
- 內政部簽發的憑證我們只核對過少數幾張的格式。格式不同的憑證（發證者名稱超過 127 個位元組、簽章演算法不同）會被電路拒絕，這是看得見的失敗。上線前要用不同年份的卡片試過。
- 展期的憑證是新的序號、同一把金鑰（憑證實務作業基準 4.6 節），匿名編號不變；持卡人要用展期後的憑證才過得了卡。
- 既然動了電路，會想順便加別的功能。每多一項，「差異一眼看得完」就弱一分；其他改動各自另寫 ADR。第二項是 ADR-0009（公鑰的位置從結構推導）。
