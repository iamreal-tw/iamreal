# 每一份證明由另一份實作重驗一次，之後靠雜湊確認沒有變

名冊上的每一筆紀錄，寫入時由後台驗證一次（ADR-0023）；公布之後，再由 Go 的重驗指令（`iamreal-verify`，用原生的 `bb`）驗證一次證明、套用一次名冊規則。這一筆之後不再重驗證明，只確認它的雜湊沒有變。營運者每天排程跑一次這個重驗，跑在 GitHub Actions，不在後台。舊紀錄的證明不照日曆定期重驗。

這一份取代 ADR-0014 Consequences 最後一條的最後一句（「後台每次發布快照前，自己用 `roster/` 完整重算一次」）。

先前的做法是每天發布前把每一份證明重驗一次。驗一筆約 12 ms（[實測](https://github.com/iamreal-tw/iamreal/issues/16)），一百萬筆單核心約 3.3 小時；名冊正常的量約兩年到一百萬筆，最糟的量一個月內到（[用量估計](https://github.com/iamreal-tw/iamreal/issues/2)）。ADR-0023 之後名冊檔寫滿就公開，重驗也不再是發布前的關卡，是公布之後的檢查。

重驗要抓的錯有兩種，抓法不同：

- **後台收了不該收的紀錄**（驗證或名冊規則的程式有錯）。同一份程式再驗幾次答案都一樣，要另一份實作才抓得到。每一筆由另一份實作驗一次就夠。
- **紀錄寫入之後變了**（存著的檔案壞掉或被動過）。重算紀錄的雜湊，和名冊指紋比就知道（ADR-0021）。雜湊沒變，驗過的證明就還是驗得過。

## 營運者每天的重驗

和任何人做的重驗是同一支指令、同一份公開的檔案。它做四件事：

1. **新增的紀錄**：從上次做到的下一筆開始，檢查寫法、驗證證明、套用名冊規則；算出來的名冊指紋和雜湊清單，和公布的核對。
2. **新增的清冊**：重新驗章、建樹，和清冊存檔的索引核對。
3. **舊的名冊檔**：每一檔至少每 30 天重新下載一次、重算雜湊，和自己記著的那一檔結尾的名冊指紋比。不重驗證明。
4. **卡片狀態檔**：後台存的每張卡片的規則狀態，和自己從名冊算出來的逐張比。

**進度檔**是重驗的人自己的暫存：做到第幾筆和那時的名冊指紋、每一檔結尾的名冊指紋、每張卡片的規則狀態、看過的題目、驗過的清冊，和是哪一版的指令、`bb`、名冊規則算的。丟了就從第 1 筆重來，結果要相同。營運者的進度檔放在 GitHub Actions 的快取，不公布給別人當起點：拿別人的進度檔，等於相信那個人。

**卡片狀態檔**由後台每天寫一份，和名冊一起公開：一張卡片一列，每一列帶這張卡片最後一筆紀錄的序號。後台寫這份檔時，筆數和每張卡片的狀態是在同一刻讀出來的，就是指紋檔同一天那一行的筆數；讀完才寫檔，寫的時候照常收過卡，不必停下來。重驗的人做到第 N 筆時照 `spec/roster-rules.md`「Comparing」比：列的序號超過那一行筆數的卡片算不同；N 還不到那一行的筆數時，序號超過 N 的卡片下一次再比。只留最近 7 天的；更早的任何一天都能從名冊重算。

**從第 1 筆整份重驗**由事件觸發：`bb` 或重驗指令換了版本、名冊規則的版本號加了一號、進度檔不見或不可信。驗證證明不需要前後文，可以分段同時跑；名冊規則照順序另外算。

## 沒有通過時

| 發現了什麼 | 處理 |
|---|---|
| 新增的紀錄裡有一筆無效 | 停止收過卡，查原因 |
| 卡片狀態檔和重算的不同 | 停止收過卡，查原因 |
| 公布的名冊指紋或雜湊清單和重算的不同 | 停止收過卡，查原因 |
| 舊名冊檔的雜湊變了 | 不停止收過卡；從備份換回那一檔 |
| 沒辦法檢查（下載不到、排程沒跑） | 不算沒有通過；下一次接著做 |

- 停止收過卡由營運者手動做。重驗的工作不握有能控制後台的金鑰。
- 無效的那一筆留在名冊上，照 ADR-0014：照樣列出，不改變任何狀態。
- 兩份實作不一致時，以 `spec/` 的規格和標準答案為準。修錯的那一份，並把這個案例加進 `spec/vectors/`。錯的是後台時，名冊規則的版本號加一號，從紀錄重建每張卡片的狀態，才恢復收過卡。
- 每一次都開一張公開的 issue：第幾筆、哪個代碼、原因、怎麼修的。

## 理由

- **重複驗同一筆，換不到新的保證。** 證明驗不驗得過只看紀錄的內容。內容有沒有變，雜湊就回答了。
- **檢查的一方和被檢查的一方不是同一份程式，也不在同一家的機器上。** 後台是 TypeScript 和 WASM 的驗證，跑在 Cloudflare；重驗是 Go 和原生的 `bb`，跑在 GitHub Actions。後台那一邊的程式或資料出問題時，檢查的一方不會跟著錯。
- **營運者跑的就是外面的人跑的。** 重驗只從公開的網址下載檔案，不需要後台的任何金鑰；別人拿同一個工作流程檔就能自己跑。每天跑的那一條也就是整份重驗會用的那一條，平常就在用。
- **結果本來就公開。** 每天的執行紀錄在公開的程式庫上看得到。
- **一條規則用到名冊變大。** 每天的工作量只跟當天新增的筆數和名冊的三十分之一走，不必在名冊到某個大小時換做法。

## Considered Options

- **照日曆定期從第 1 筆整份重驗**（每週或每月）：用同一份指令重驗沒變的紀錄，答案不會不同；要防的兩種錯已經各有抓法。
- **在後台的排程裡用 TypeScript 重驗**：和後台是同一份程式，抓不到程式本身的錯；一次排程最長 15 分鐘（[整個後台放在 Cloudflare 上，有哪些元件可用、各有什麼限制](https://github.com/iamreal-tw/iamreal/issues/6)），整份重驗做不完。
- **在 Cloudflare Containers 跑 Go 的重驗指令**：做得到，執行的部分都留在同一家。沒有採用，因為要多維護容器映像檔、啟動它的程式和公布結果的地方，而且檢查的一方和後台在同一家的機器上。
- **重驗沒有通過時自動停止收過卡**：重驗的工作要握有能控制後台的金鑰，執行機出一次狀況就可能誤停。過卡可以停 24 小時（[用量估計](https://github.com/iamreal-tw/iamreal/issues/2)），重驗本來就晚一天，手動停多出來的幾個小時可以接受。
- **卡片狀態只公布一個摘要，或只公布當天有變的卡片**：摘要比出不同時不知道是哪張卡片；只看有變的卡片，抓不到「沒有人過卡，存著的那一列卻變了」。
- **後台開一個介面讓人分頁讀卡片狀態**：讀取會和過卡擠在同一個 Durable Object，還要為它限流。寫成檔案，下載不經過後台的程式。
- **舊名冊檔每週整份重算一次雜湊**：名冊小的時候可以，大了之後一次做不完，要再換做法。
- **公布營運者的進度檔，或把整份名冊打包成一個檔**：前者是請人相信營運者；後者是多一份要維護的東西，分檔下載本來就能接著做。

## Consequences

- **每天公布的名冊指紋不表示那天的紀錄已經被另一份實作重驗過。** 它保證的是紀錄沒有被拿掉、順序沒有變（ADR-0021）。重驗最多晚一天。對外的說明照實寫。
- **`iamreal-verify` 要做到四件事**：讀寫進度檔、接著上次做；指定一段序號只驗那一段的證明；直接讀網址、不必先把整份名冊存到磁碟；清冊也只處理新的。
- **公布的檔案多一種**：卡片狀態檔。名冊目錄、雜湊清單、指紋檔、清冊存檔不變。
- **多依賴一項 GitHub 的服務。** 一個工作最長 6 小時（[limits](https://docs.github.com/en/actions/reference/limits)）；排程在尖峰時會延後，公開的程式庫 60 天沒有活動時排程會被停掉（[schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)）；快取 7 天沒有被讀就刪掉，一個程式庫上限 10 GB（[dependency caching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)）。排程沒跑要有人知道，和「沒有通過時通知營運者」一起在監控的決定裡定。快取不見的後果是一次整份重驗。
- **後台每天把整張卡片狀態表讀出來寫成檔案，要多久還沒有量。** 量出來會卡住寫入，就改成分幾天輪完一遍。
- **「從備份換回那一檔」的備份放在哪裡**，定在 ADR-0033：那一份叫副本，換回的步驟也在那裡。
- **Go 的重驗指令是這個做法的前提。** 它不設期限地留著；要拿掉，先要有另一份獨立的實作，不然這一份要重開（ADR-0030）。
- 「每日快照」不再指一個步驟。快照是名冊到某一天指紋檔那一行為止的那一段（`GLOSSARY.md`）。
