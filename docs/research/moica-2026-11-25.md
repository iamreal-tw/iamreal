# 研究：內政部 2026-11-25 的兩則公告對服務的影響

[#498](https://github.com/iamreal-tw/iamreal/issues/498) 的研究結果，2026-11-27。這份文件只記查到的事和每一項影響的判斷，不改程式；要改的另外開票。

## 結論

兩則公告都沒有讓現在的程式壞掉的證據。HiCOS 3.2.10 沒有公開改了什麼，網頁過卡在 Windows 上從來沒有試過，要不要實測由維護者決定。作業基準 2.2 版裡，這個程式庫引用的每一節文字都和引用的相同；沒有官方的修訂對照表，所以只對了引用的那幾節。

| 項目 | 判斷 | 理由在 |
|---|---|---|
| 網頁呼叫元件的方式（網址和埠、回應格式、來源檢查、簽章流程） | 要維護者決定：要不要在 Windows 上實測 | 「呼叫方式有沒有變」 |
| 過卡頁對元件版本的假設 | 不用改 | 「過卡頁現在的假設」 |
| 瀏覽器的本機網路權限 | 不用改 | 「瀏覽器的本機網路權限」 |

## HiCOS 卡片管理元件 3.2.10

### 公告說了什麼

內政部 2026-11-25 [1]：

> HiCOS卡片管理元件已更新至3.2.10版。本次改版已由中華電信研究院完成相關驗證測試，並通過資安檢測，整體提升資安防護能力與系統穩定性。建議儘速更新至3.2.10版，以確保自然人憑證於最新作業系統環境下可正常運作並支援相關應用服務。

> 如使用者近期操作憑證時遇到安裝問題或出現系統錯誤，建議先移除舊版元件後，下載並安裝3.2.10版

問答第 1、4 題只講 Windows：「全面支援 Windows 10及Windows 11作業系統」、「建議於 Windows 10（含）以上版本之作業環境中使用」。

- **沒有列出改了什麼。** 公告的字和 2026-10-08 的 3.2.9 公告 [7] 除了版本號碼以外相同（逐段對過），兩則都沒有修正項目、漏洞編號或受影響的版本
- **中華電信的版本說明沒查到。** 中華電信的下載頁 [4] 只有版本號碼和下載點，沒有改版說明；搜尋也沒有找到中華電信發布的 3.2.10 說明
- **「資訊安全」指的是什麼，沒查到。** 公告只說「通過資安檢測」「提升資安防護能力」，沒有說修補了哪一個漏洞

### 3.2.10 是哪一個作業系統的

是 Windows 的安裝包。依據：

- 內政部 2026-01-26 的公告寫「HiCOS Client 套件（含卡片管理工具軟體與跨平台元件網頁元件）」[8]。Windows 上，網頁過卡用的「跨平台網頁元件」和卡片管理工具裝在同一個安裝包裡；版本號碼「3.2.x」是這個安裝包的
- 中華電信的下載頁 [4]（2026-11-27 讀，頁面的 `Last-Modified` 是 2026-11-20）：「下載Windows版 (Hicos 3.2.9)」、「下載Mac版(1.3.5.1)」、「下載Linux版(1.3.4.7)」。Windows 的那一行還寫 3.2.9
- 但那一行連的 `HiCOS_Client.zip`（`api-hisecurecdn.cdn.hinet.net/MOICA/HiCOS_Client.zip`）2026-11-27 的回應標頭是 `last-modified: Wed, 25 Nov 2026 00:55:45 GMT`、`content-length: 38631289`；3.2.9 的那一份（`storage.nat.gov.tw/moda-data/HiCos 3.2.9/HiCOS_Client.zip`）是 `last-modified: Fri, 16 Oct 2026 03:54:59 GMT`、`content-length: 38532958`。公告當天換了一個不同的檔，推測就是 3.2.10（沒有打開來看）
- macOS 的 `HiPKILocalSignServer.pkg`（`api-hisecurecdn.cdn.hinet.net/HiPKILocalSignServer/mac/`）的 `last-modified` 是 2023-06-08，沒有跟著換

所以 macOS 上的持卡人不受這次改版影響；Windows 上的會。

下面說的「元件」都是網頁過卡用的跨平台網頁元件（`localhost:61161`，版本是 `1.3.x`）；「HiCOS 3.2.x」是 Windows 上包含它的整個安裝包。

### 過卡頁現在的假設

`web/src/card/hipki.ts`、`web/README.md`「元件的橋接信任什麼」：

- 元件在 `http://localhost:61161`，寫死在 `web/src/target*.ts`
- 頁面用 `window.open` 開 `/popupForm`，等視窗送來 `{"func":"getTbs"}`，送一個請求，收一個回應；只收來源是 `http://localhost:61161` 的訊息
- 用到的請求只有兩個：`GetUserCert`（讀憑證）、`MakeSignature`（`tbs`、`hashAlgorithm: "SHA256"`、`signatureType: "PKCS1"`、`pin`）
- 回應讀的欄位：`ret_code`、`last_error`、`slots[].slotDescription`、`slots[].token.certs[].certb64`、`signature`（256 個位元組）、`certb64`。錯誤碼是讀程式得知的，沒有實測
- **不看元件的版本。** 頁面不讀回應裡的版本欄位，也沒有最低版本；不認得的回應一律停下、顯示代碼，不重送

這些都是在 macOS 上、對 macOS 的元件測的（`web/README.md`「已知的限制」：「只在 macOS 上的 Chrome 測過」）。Windows 上的元件，不論哪一版，都還沒有用過卡的頁面試過。

### 呼叫方式有沒有變

**沒有辦法從文件知道。** 公告和中華電信的頁面都沒有寫元件的網址、埠、請求或回應有沒有變。

從其他官方頁面看得到的：

- 中華電信的下載頁 [4] 和政府憑證管理中心的 HiCOS 頁 [5] 2026-11-27 都還連到 `http://localhost:61161/selfTest.htm`（「檢視目前已安裝版本及IC卡自我檢測」），埠還是 61161
- 政府憑證管理中心的版本檢測頁 [6] 的程式有一張元件版本和 HiCOS 版本的對照表，最新的一列是 `1.3.4.103353` 對 `3.2.9.11006`，沒有 3.2.10 的那一列。同一段程式在回應的 `ret_code` 是 `0x76000031` 時跳出「非信任網站，請先加入信任網站」：元件有一份信任的網站清單，至少有一種請求會看它。`web/README.md` 的錯誤碼表裡也有 `0x7600000F`（禁止存取的網域）。哪些請求會看這份清單、`/popupForm` 的請求會不會、3.2.10 有沒有改，都沒有查到

開發用的 macOS 電腦上的元件 2026-11-27 用 `web/test/e2e/check-component.ts` 問過一次 `CheckEnvir`（這支程式只送這一個請求）：`ret_code` 0，回應的 `version` 是 `"2.3.3"`，頁面是跨來源隔離的，沒有違反 CSP。這個 `version` 和上面的 `1.3.5.1`、`1.3.4.1033xx` 都對不上，是什麼的版本沒有查到。macOS 的元件沒有跟著改版，所以這一次看不出 3.2.10 的任何事。

**判斷：要維護者決定。** 要知道 3.2.10 會不會讓網頁過卡壞掉，只有在一台 Windows 上裝 3.2.10，用測試網站（`test.iamreal.tw`）真的過一次卡。建議做：Windows 上從來沒有試過，這件事和 3.2.10 無關也該做。最可能壞的地方是上面那份信任的網站清單：如果元件開始對 `/popupForm` 的請求檢查網站，`iamreal.tw` 不在清單上，過卡會停在第 2 步，顯示代碼（`card_error`）。

### 瀏覽器的本機網路權限

Chrome 142 起，公開的網站連到本機（`localhost`）要使用者允許（Local Network Access）[9]。Chrome 的說明 [10]：

> enforcing checks **only** when a request crosses from a *less private* address space into a *more private* address space

說明列的是 `fetch()`、子資源、子框架的導覽 [9]，沒有提到 `window.open` 開出的視窗。

過卡頁本身不對 `localhost:61161` 發任何請求（`web/README.md`「`Content-Security-Policy`」：「頁面本身不對 `localhost:61161` 發任何請求，那些請求是元件的頁面自己發的」）；元件的視窗是 `localhost` 的頁面，它對 `localhost` 的請求不跨位址空間。營運者 2026-11-21 在測試網站（`https://test.iamreal.tw`，公開的網站）用真卡片走完過卡（[#71](https://github.com/iamreal-tw/iamreal/issues/71)；票上沒寫作業系統和瀏覽器）。

**判斷：不用改。** 這和元件的版本無關：公告沒有提到瀏覽器，頁面也沒有新的請求。

### 舊版還能不能用

- 公告沒有說舊版不能用，也沒有停用舊版的日期。說法是「建議儘速更新」、「仍建議更新至3.2.10版」[1]
- 政府憑證管理中心的版本檢測頁 [6] 判斷「請立即升級」的門檻是 `WinVer = "1.3.4.103349"`（對照表裡是 HiCOS 3.2.5），macOS 是 `1.3.5.1`
- 沒有查到 3.2.10 修補了哪一個漏洞（上面「公告說了什麼」）

過卡頁要提醒更新的話，有兩種做法：

1. **過卡的畫面去問元件的版本，太舊就提醒。** 不建議：頁面要讀回應裡的版本欄位，但那個欄位是什麼的版本沒有查到（上面的 `"2.3.3"`）；政府憑證管理中心的做法是頁面用 `<img>` 去讀 `http://localhost:61161/p11Image.bmp` [6]，那是頁面自己對本機發請求，現在的 CSP（`img-src 'self'`）不准，也會碰到上一節的本機網路權限
2. **「過卡需要什麼」（`/prepare`）加一句。** 現在的第 1 步是「下載並安裝內政部的「跨平台網頁元件」」，沒有講已經裝過的人。可以加「已經裝過的，也到同一頁下載最新版重新安裝」，和內政部建議的「先移除舊版元件後，下載並安裝」[1] 一致；「需要什麼」的「Windows 或 macOS 的電腦」可以寫成 Windows 10 以上（[1] 的問答第 4 題、[5]「新版HiCOS卡片管理元件僅支援作業環境Win 10/11，且不向下相容」）

**判斷：要維護者決定。** 建議第 2 種，不做第 1 種。那一頁的字照 `design/copy/prepare.md` 的規則，每一個對內政部的說法附來源；要改的話另開票。

### 手機 app

HiCOS 是電腦上的軟體。Android、iOS 的 app 用 NFC 直接和卡片溝通（`android/`、`ios/`、`device-core/`），不經過 HiCOS 或跨平台網頁元件。**判斷：不用改。** app 讀卡的部分另外看過。

## 憑證實務作業基準 2.2 版

### 公告說了什麼

內政部 2026-11-25 [2]：

> 內政部憑證管理中心憑證實務作業基準第2.2版，業經數位發展部審查，符合「數位簽章憑證實務作業基準」應載明事項。依電子簽章法第12條第1項及第2項規定，公布旨揭憑證實務作業基準，供民眾查詢。

### 原文和修訂紀錄

讀的是儲存庫 [12] 上唯一的一份「內政部憑證管理中心憑證實務作業基準.pdf」[11]（1,023,961 位元組，105 頁）。封面「第 2.2 版」、「中華民國 115 年 06 月 01 日」；PDF 的文件標題是 `內政部憑證管理中心憑證實務作業基準_V2.2_20261125.docx`。

- **修訂紀錄沒有寫改了什麼。** 「版本修訂歷程」那一頁，2.2 版這一列是「2026-06-01　修正通過「內政部憑證管理中心憑證實務作業基準」第 2.2 版。」，和前面每一版一樣只有這一句
- **沒有修訂對照表。** 儲存庫只列這一份作業基準，沒有對照表 [12]
- **生效日期和公布日期對不上。** 修訂紀錄的生效日期是 2026-06-01，公告是 2026-11-25。1.2 節寫「公布日期：115 年 06月　　日」，日期是空的；摘要的「主管機關核定文號：」後面也是空的
- **第 2.1 版沒有拿來比。** 儲存庫上已經換成 2.2 版

所以**沒有官方的修訂對照表，只對了這個程式庫引用的各節**：每一節在 2.2 版裡的文字，和 ADR、規格引用的說法是不是還相同。2.2 版改了哪些別的地方，不知道。

### ADR 和規格引用的各節

| 2.2 版的節（頁） | 2.2 版的原文 | 引用的地方 | 還相同嗎 |
|---|---|---|---|
| 4.1.1（20） | 「18 歲以上，設籍於我國之國民或持有居留證之外來人口，且未受監護宣告者。」 | ADR-0011：外來人口也能申請 | 相同 |
| 4.6（26） | 「簽發1張與原憑證具有相同憑證主體名稱、金鑰及相關資訊的新憑證，新憑證只對有效期限(notAfter)予以展延一段時間，給予1個新的憑證序號。」 | ADR-0008：展期是新序號、同一把金鑰 | 相同 |
| 4.9.3.2（33–34） | 「廢止之憑證最遲於憑證廢止清冊下次更新時間(NextUpdate)前加入憑證廢止清冊中，並將憑證狀態資訊公告於儲存庫，直至該廢止憑證到期為止。」 | ADR-0008 | 相同 |
| 4.9.7（35） | 「憑證廢止清冊每日至少簽發 1 次，其有效期限不超過 36 小時。」 | ADR-0015、`spec/revocation-tree.md` | 相同 |
| 4.10.1（39） | 「憑證廢止清冊或線上憑證狀態協定回應訊息中之憑證廢止資訊，須至該被廢止之憑證已過期後始可移除。」 | ADR-0008 | 相同 |
| 6.1.1.2（54） | 「行動自然人憑證的金鑰對是在用戶信賴之行動載具內產製，且金鑰對產製完畢後，其私密金鑰無法由行動載具內部匯出。」 | ADR-0011 | 相同 |
| 6.3.2.2（58–59） | 「公開金鑰憑證之使用期限為5年，私密金鑰之使用期限為5年，於效期到期時得展期1次，且為期3年，而使公開金鑰及私密金鑰的使用期限最長為8年。」 | ADR-0018 | 相同 |

**判斷：** ADR 的內容不用改。ADR 記的是當時的依據，寫的版本（v2.1）不改。`spec/revocation-tree.md` 是現行的規格，寫「CPS v2.1 section 4.9.7」，儲存庫上已經沒有 2.1 版，**要改**成 2.2 版的同一節（文字相同，規則不變）。

順帶讀到、和現在的設計一致的：

- 4.6.2：展期的期間是「在憑證到期前的60天開始至到期後3年內」。過期之後還能展期，展期後是同一把金鑰，所以同一個匿名編號又能過卡。ADR-0008 已經寫了「展期不換金鑰，匿名編號不變，到期後還能過卡」
- 3.2.3.3：可以「線上申請憑證換發」。換發是新的金鑰，新的匿名編號（ADR-0020「換卡就換網址」）

### 憑證的格式和欄位

電路檢查的欄位裡，金鑰用途、持卡人類別、憑證政策這幾項（ADR-0010、ADR-0011）**作業基準沒有寫**，它把格式交給另一份文件：

- 7.1（62）：「憑證管理中心簽發的憑證之格式剖繪依照本基礎建設技術規範相關規定。」
- 7.1.2（62）：憑證擴充欄位「依照本基礎建設技術規範相關規定」
- 7.1.6（63）：憑證政策物件識別碼「使用本基礎建設之憑證政策物件識別碼」
- 7.1.9（63）：憑證政策擴充欄位的關鍵性「須依據政府機關公開金鑰基礎建設憑證及憑證廢止清冊格式剖繪之規定」

作業基準自己寫了的：X.509 v3（7.1.1）、主體公開金鑰的演算法是 `rsaEncryption`（7.1.3）、主體和簽發者用 X.500 的識別名稱（7.1.4），都和電路的假設相同。金鑰長度和簽章演算法在下一節。

那份格式剖繪這次沒有讀；作業基準 2.2 版不會讓它變，它有沒有改版要另外看。**判斷：不用改**（從作業基準看不出任何變化）。

### 作業基準寫得比電路寬的地方

電路只收一種憑證：持卡人的金鑰剛好是 RSA 2048 位元、指數 65537（ADR-0009、0010），發證單位用 sha256WithRSAEncryption 簽（`circuits/lib/src/der.nr`）。作業基準准許的比這寬：

- 6.1.5（55）：「用戶使用 2048 位元(含)以上的RSA 金鑰。」6.3.2.2 也寫「金鑰長度為RSA2048位元(含)以上」
- 7.1.3（62）：發證的簽章演算法「可為其下任一種」：sha256WithRSAEncryption、sha384WithRSAEncryption、sha512WithRSAEncryption。同一份的 6.1.5 又寫「以及SHA256 雜湊函數演算法簽發憑證」

這不一定是 2.2 版新加的（沒有和 2.1 版比）。內政部真的發出這種憑證時，電路會拒絕它：持卡人過不了卡，看得到原因，不會算錯，也不會多一個匿名編號。

**判斷：碰到電路，另開 issue 討論，不在 #498 改**（`CLAUDE.md` 硬限制：改變電路接受什麼要先開 issue 討論）。討論的是要不要記下這個差距和「內政部發出第一張這種憑證時怎麼發現」；建議不改電路：現在沒有這種憑證，電路也沒辦法先為不知道長什麼樣的憑證寫好。

### 發證金鑰

作業基準沒有列出發證金鑰，也沒有寫 G2、G3 或第幾代。儲存庫上有「MOICA憑證下載(第二代).cer」「(第三代).cer」兩個連結 [12]，和 `spec/issuers.md` 的兩代相同（連結的網址沒有記下來，沒有和 `spec/issuers.md` 的網址逐一對）。

6.3.2.1（58）：發證金鑰「使用期限至多為20年，以私密金鑰執行簽發憑證用途之使用期限至多為10年」。G3 的發證憑證從 2024-01-23 起（`spec/issuers.md`），照這一條最晚 2034 年就要有下一代。`spec/issuers.md` 的規則已經寫了「A key is added as a new row when MOICA introduces one」，新的一代需要它那個長度的電路。

**判斷：不用改。**

### 廢止清冊

- 作業基準：每天至少一次、每份有效不超過 36 小時（4.9.7）；2.3 節「憑證管理中心每日至少簽發並公告 1 次憑證廢止清冊，公布於儲存庫」；完成廢止後 24 小時內重新簽發（4.9.7 第 2 點）
- 作業基準**沒有寫**清冊的網址、檔案大小、分不分割。7.2.2 說清冊的延伸欄位照《政府機關公開金鑰基礎建設憑證及憑證廢止清冊格式剖繪》，沒有列出是哪些
- 儲存庫的頁面 [12]：「本清冊於每日凌晨零時及中午12時產製，與憑證用戶之實際憑證狀態最長會有12小時的時間差」，列「憑證廢止清冊(第二代)完整清單.crl」「憑證廢止清冊(第三代)完整清單.crl」兩個連結，兩代各一份完整的清冊

對照現在的做法：鏡像每小時抓一次；規格要的是完整、不分割的清冊（`spec/revocation-tree.md`「Which CRLs」）；3 天的上限建立在「每天至少一次」上；下載上限 32 MiB，2026-11-26 的大小是 G2 16,829,939、G3 8,933,251 個位元組（`worker/README.md`）。都還成立。

**判斷：不用改。**

### 卡片的種類和換發

- 4.1.1：國民和持有居留證的外來人口都能申請。電路只收國民（ADR-0011）
- 行動自然人憑證：金鑰在手機上產生（6.1.1.2）；6.3.2.2「公開金鑰憑證之使用期限為1年……效期到期後不得展期，需重新產製金鑰對」。電路不收行動自然人憑證（ADR-0011）
- 4.10.4「行動載具異動管理」講行動自然人憑證換手機等情況，和實體卡無關
- 作業基準沒有提到新一代的實體卡片

**判斷：不用改。**
